# Feature: end-to-end testing and live polls

## Task

Add a Playwright-driven E2E package under `packages/e2e`, executed by Vitest.
The suite must run against a started local API and web application, reset and
seed the database before each run, and execute serially. Provide a headed mode
for manual flow inspection.

Implement the product flows required for E2E coverage. This includes
authentication, public poll browsing, live-poll creation and voting, and the
supporting API endpoints. Add Artillery load-test configuration, CI execution,
and deployment protections needed for these flows.

## Full task context and specifications

Implement all user stories and possible user flows in `packages/e2e` with
Playwright.

- Start E2E tests with `pnpm -F e2e test` for CI, or with
  `pnpm -F e2e test:ui` for headed and slowed execution. Vitest runs the tests
  and controls Playwright.
- Start the API and web application environment before running tests.
- Reset and seed the database from the Vitest global setup file. Invoke the
  `0-cleanup.ts` seed.
- Do not run tests concurrently because races can affect data and assertions.
- Use a 50 ms delay while typing and a 500 ms delay while clicking or tapping
  in headed, human-visible execution.

If functionality is missing from the following specifications, implement it:

- E2E must run existing and missing product stories.
- Required E2E scenarios must cover authentication, poll creation and every
  ballot type, eligibility rejection, private-group access, invitations,
  results, settings, subscriptions, payment outcomes, and live-poll states.
  - Invitations create only an in-app pending record and a shareable link. Do
    not send email yet.
  - Settings allow email and password changes only.
  - Subscriptions and payment outcomes use mocked payments.
- Use AWS SES as the email provider.
- Use Server-Sent Events (SSE) as the real-time protocol for live polls. The
  target is 1,000 concurrent users voting.
- Validate Chrome in English at 1280 px wide on desktop and 480 px wide on
  mobile.
- Ignore accessibility standards.
- Test execution relies on provisioned database state and resets and seeds the
  default data on every run.
- Poll results are visible to everyone while a poll is open or closed.
- Do not implement tie-breaking or exhausted-ballot handling yet.
- Unauthenticated users can browse and view poll details. Voting requires
  login.
- Users cannot change demographic data. Eligibility and results use a snapshot
  of demographic data at the time of voting.
- Polls are binding. Governance, audit trails, vote secrecy, tamper evidence,
  and result certification are out of scope for now.
- Notifications are out of scope for now. Do not send email or push
  notifications.
- Future payment providers are credit card, PayPal, and Apple Pay.

### Plan lifecycle

- The free plan is the default. A user can upgrade after registration.
- A downgrade does not refund money. Add this to the terms.
- An upgrade starts on the upgrade date and does not refund money. Add this to
  the terms.
- A cancellation stops automatic charges at the end of the month.
- During an upgrade or downgrade, collect invoice details for the next invoice.
  Users cannot change these details. They must cancel and subscribe again.

### Billing

- Use EUR.
- Invoice fields are legal name, tax ID or VAT ID, address, postal code, city,
  and country. Prefill available user data except the VAT number.
- Keep invoices neat and minimal.
- Apply downgrades immediately.

### Plan-limit downgrade behavior

- If the current groups exceed the new plan limit, delete all groups only after
  the user confirms. If the user does not confirm, do not downgrade or delete
  data.
- When current groups exceed the new plan limit, delete currently open group
  polls and all current group invitations.
- A downgrade of an open live poll removes all current attendees. They must
  open the QR-code link again so the new limit is enforced.

### Canonical routes

- Use `/poll/list` and `/poll/:id/results`.

### Live-poll state model and quota

- An attendee who reconnects within 60 seconds keeps the same attendee identity
  and slot.
- A closed live poll cannot reopen. Its attendee data and final result remain
  available.
- The quota is based on concurrent attendees who opened the QR-code link and
  are on the live-poll page.
- The heartbeat and disconnect timeout is 60 seconds.
- Reject a vote submitted as the poll closes. The page should refresh and show
  that the poll is closed before this happens.
- Test 1,000 concurrent users voting with Artillery.

### Acceptance criteria

- A developer can run E2E specifications in headed mode and observe Playwright
  acting as the user at a speed suitable for manual inspection.
- `pnpn -F e2e test` succeeds.
- Load testing meets these measures:
  - SSE connections last 60 seconds.
  - Vote submission rate is 100 votes per second.
  - Maximum error rate is 1%.
  - p99 response time is below 100 ms.
  - The test environment is local.

## Problem

The repository had API and web application tests, but it did not validate user
flows through a real Chromium browser. There was no dedicated E2E package,
repeatable database setup for browser tests, headed mode for inspecting browser
actions, or CI job that ran browser flows.

Live-poll UI states used local placeholder data. The API did not provide routes
to create or open a live poll, register a live attendee, submit an attendee
vote, retrieve a poll by ID, or receive a live-poll event. Account email and
password changes also had no API support.

There was no scheduled load-test workflow or application ingress rate limiting.

## Solution

- Added the `packages/e2e` workspace package with Vitest, Playwright, Artillery,
  and a serial test configuration.
- Added global setup that loads local environment values, applies API
  migrations, clears the database, seeds plans, users, polls, and domain data,
  then closes the database connection after the suite.
- Added Playwright helpers for English Chromium sessions, desktop and mobile
  viewports, headed slow-motion execution, typed input, and optional browser
  pause.
- Added browser scenarios for registration, seeded-user login, and public poll
  browsing through poll details and results.
- Added a desktop creator and mobile voter live-poll scenario. It creates and
  opens a live poll, joins as an attendee, waits for the poll, selects an
  option, and submits a vote.
- Added live-poll contracts and API routes to create and open polls, retrieve a
  poll, join or reconnect as an attendee, submit attendee votes, and receive a
  Server-Sent Event containing the poll state.
- Added live-poll service logic for attendee tokens, attendee heartbeats, poll
  opening, and vote persistence. Live poll creation sets the poll type,
  availability, and unrestricted demographics used by the current UI flow.
- Connected the live-poll web application to the API for creation, opening,
  attendee registration, poll retrieval, and vote submission. Added a
  copyable voter link.
- Added authenticated endpoints for changing the current user's email address
  and password, including duplicate-email and current-password validation.
- Updated live-poll component tests for asynchronous API interactions.
- Added Artillery configuration and an authentication, current-user, and poll
  retrieval load scenario. The load configuration fails when the error rate is
  above 1%, p95 is above 100 ms, or p99 is above 250 ms.
- Added a scheduled and manually dispatchable GitHub Actions load-test workflow
  for the dedicated self-hosted load runner.
- Added E2E execution to CI and corrected the web application package selector
  used by the existing CI test job.
- Added Traefik rate-limit middleware for API and web application ingress.
- Updated the README with E2E and load-test commands and execution guidance.

## Run locally

Start the local environment and seed the database first. Then run:

```sh
pnpm -F e2e test
```

Run the headed browser UI with visible actions:

```sh
pnpm -F e2e test:ui
```

Run each Artillery scenario:

```sh
pnpm -F e2e test:load
```

## Verification

- The CI workflow runs `pnpm -F e2e test` after API and web application tests.
- Browser tests use Chromium in English at 1280 × 700 for desktop flows and
  480 × 700 for the mobile live-voter flow.
- The E2E Vitest configuration disables test-file parallelism and limits
  concurrency to one.
